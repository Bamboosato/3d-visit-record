## 2. 目的と利用シーン

### 2.1 背景と目的
初版（v1）の 3D Visit Record は、訪問済み・訪問予定の地点を 3D 地形視点・From-To 期間・複数行メモとともに記録し、Google Drive へ安全に同期できる基盤を実現しました。しかし旅行や登山・散策の体験を振り返る上では、テキストメモに加えて **「その場所・その訪問回で撮影した写真」** をログごとに残したいというニーズが不可欠です。

v2.0 では、初版の強みである **サーバーレス運用（開発者側 DB・ストレージ維持費ゼロ）・高速な 3D 描画・堅牢なローカル保存・`drive.file` 単一スコープによる安全なクラウド同期** を損なうことなく、訪問記録ログへ写真を添付・圧縮・閲覧・同期できる仕組みを追加します。

### 2.2 想定利用シーン

| ユーザー / シーン | 具体的な利用イメージ |
| :--- | :--- |
| **現地・帰宅後の訪問記録作成** | スマートフォンのカメラロールまたは PC の写真フォルダから、訪問済み地点（新規登録・再訪追加・予定→訪問済み確定）のログへ最大 5 枚の写真を添付し、思い出の一言キャプションを添えて保存する。EXIF の撮影日が残っていればワンタップで訪問日に反映できる。 |
| **地図・一覧からの振り返り** | 登録地点一覧カードに表示される代表サムネイルや枚数バッジを手がかりに地点を探し、詳細シート内のサムネイルからライトボックスで景色を拡大閲覧する。 |
| **PC ⇔ スマホ間のマルチデバイス同期** | 旅先でスマホから登録・写真添付して Google Drive に保存し、帰宅後に PC で復元。復元時は軽量なメタデータのみ即座に同期し、写真本体は閲覧した地点からオンデマンド取得（または任意の一括ダウンロード）することで端末容量と通信量を節約する。 |
| **写真の整理・差し替え** | 不要になった写真や重複写真を削除し、並び替えで代表写真を変更する。削除済み写真は Undo による復元安全性を確保しつつ、Google Drive 保存時にゴミ箱へ自動整理してクラウド容量の肥大化を防ぐ。 |

## 3. v2.0 スコープ定義

### 3.1 v2.0 に含まれる範囲（In Scope）
1. **訪問済みログへの写真添付・編集**: 新規地点登録（訪問済み）、訪問記録追加、訪問済みログ編集、「訪問予定 → 訪問済み」確定フォームにおいて、1 ログ最大 **5 枚** の写真を添付・並び替え（先頭＝代表写真）・キャプション入力（最大 200 文字）・個別削除できる。
   - **対象ステータス方針**: 写真添付 UI は **訪問済み（`kind === 'visited'`）ログのみ** に表示する。ただしデータモデル上の `VisitEntry.photos` は維持し、万一写真付きログを「訪問予定（`planned`）」へ変更した場合も既存写真を破壊せず保持・閲覧可能とする。
2. **クライアント側リサイズ・圧縮・EXIF 処理**: 端末内で閲覧用本体（長辺最大 **1,600px**、WebP 品質 `0.82` / iOS Safari 等は JPEG 品質 `0.85` フォールバック）およびサムネイル（長辺最大 **320px**、品質 `0.75`）を自動生成する。元画像から撮影日時（`takenAt`）のみ読み取って訪問日への反映を提案し、Canvas 再エンコードにより **GPS 位置情報やカメラ機種等の EXIF は完全除去** する。
3. **閲覧体験（標準セット）**: 詳細シート（`SpotDetailSheet`）のサムネイル一覧、フルスクリーン拡大ライトボックス（前後切替・キャプション・撮影日時・単体保存/共有）、登録地点一覧カード（`SpotNavDrawer`）の代表サムネイル・総枚数バッジ表示・キャプション横断検索を提供する。
4. **ローカル永続化・原子的保護**: IndexedDB（`visit3d_db`）の `photos` ストアへ本体・サムネイルを保存し、`app_state` との単一トランザクション原子的コミット、1 世代 Undo 保護、未参照 Blob の自動ガベージコレクション（GC）、端末写真ストレージ使用量表示を行う。
5. **Google Drive 同期（オンデマンド取得＋一括取得＋自動ゴミ箱整理）**: `3D Visit Record/photos/` へ本体画像をアップロード（並列上限 3・SHA-256 重複再利用・1 枚毎レジューム）。復元時はメタデータのみ即時反映し、地点閲覧時のオンデマンド取得と同期ダイアログからの任意一括ダウンロードを両立する。Drive 保存完了後は参照が外れた Drive 上の旧写真ファイルを自動でゴミ箱へ移動する。
6. **マージ整合・バックアップ案内・プライバシー更新**: 写真全削除を正しく他端末へ伝搬するマージ仕様（`photoSyncVersion: 2`）の導入、ローカル JSON バックアップ時の「写真本体非同梱」明記、3D 視点共有 URL からの写真情報完全除外、`/privacy` ページの更新を行う。

### 3.2 v2.0 の対象外（Out of Scope / v2.1 以降）
- 「訪問予定（`planned`）」ログへの下調べ参考写真の添付 UI
- 写真の EXIF GPS 座標を読み取って地図上へ新規地点を直接登録する機能
- 写真ファイル本体を同梱したローカル ZIP 形式でのエクスポート／インポート
- Google Picker API を用いた Google Drive 内既存写真の直接選択・取り込み機能（既存の `drive.file` スコープ維持で CASA 審査不要・取り込み圧縮方式で v2.0 設計へ後付け可能。ただし iOS Safari / PWA のサードパーティ Cookie 制約および追加の GCP API キー設定を要するため v2.1 の PC 向け補助導線として検討。なお v2.0 でも OS 標準ファイル選択経由での Drive 写真選択は利用可能）
- Google Photos Picker API を用いた Google フォトからの直接写真取り込み
- ナビゲーションモーダル内の独立「写真ギャラリー」タブ（全地点横断のアルバム表示）
- 3D 地図上のピンアイコンへの写真サムネイル・写真ありバッジ描画
- Drive 同期済みのローカル本体 Blob のみを解放しサムネイルだけ残す省容量キャッシュモード
- AI による自動タグ付け・キャプション生成・顔認識・OCR

## 4. 機能要件

### 4.1 写真の添付・圧縮・EXIF・編集（`F-Photo`）

| 要件ID | 機能名 | 要件内容 |
| :--- | :--- | :--- |
| **F-Photo-01** | **写真選択・添付 UI（最大 5 枚/ログ）** | フォーム（`SpotForm`）の記録ステータスが `visited` の場合（新規訪問済み登録、訪問記録追加、訪問済みログ編集、予定→訪問済み確定）、写真添付エリアを表示する。<br>・複数枚選択（`<input type="file" multiple accept="image/*">`）および PC でのドラッグ＆ドロップに対応する。<br>・`capture` 属性を付けないことで、モバイル端末では「写真ライブラリ / カメラで撮影 / ファイル」から自由に選択できるようにする。<br>・上限は **1 ログあたり最大 5 枚**、全地点合計の推奨・システム上限目安を **2,000 枚**、選択可能な元ファイル 1 枚あたりのサイズ上限を **25 MB** とし、超過時は理由を明示して受け付けない。 |
| **F-Photo-02** | **対応形式検証 & クライアント側リサイズ・圧縮** | ・JPEG / PNG / WebP（および Safari / Chrome 等がデコード可能な HEIC/HEIF）を受け付け、**SVG（`image/svg+xml` 等）および画像以外のファイルは XSS・不正データ防止のため明示拒否** する。ブラウザでデコードできない形式が選ばれた場合は再試行可能なエラー案内を表示する。<br>・EXIF の向き（Orientation）を正立化した上で、ブラウザ内 Canvas により以下の 2 画像を生成する（元画像が上限未満の場合は拡大せず元解像度を維持）：<br>　1. **閲覧用本体**: 長辺最大 **1,600px**、`image/webp`（品質 `0.82`）。`canvas.toBlob` が WebP エンコードに非対応の環境（一部 iOS Safari 等）は生成結果の `blob.type` を検査し、`image/jpeg`（品質 `0.85`）へ自動フォールバックする。<br>　2. **サムネイル**: 長辺最大 **320px**、本体と同一の有効 MIME（品質 `0.75`）。<br>・本体 Blob から SHA-256 ハッシュ（`checksumSha256`）を算出して保持する。 |
| **F-Photo-03** | **EXIF 撮影日時提案 & 位置情報等の EXIF 完全除去** | ・リサイズ前の元画像バイナリから、クライアント完結で EXIF の撮影日時タグ（`DateTimeOriginal` 等）のみを軽量解析し、`takenAt`（ISO 8601 形式および表示用日付）として保存する。**EXIF の GPS 位置情報タグは読み取らない**。<br>・添付写真から有効な撮影日が得られ、かつフォームの現在日付と異なる場合は、フォーム上に **「写真の撮影日（例: `2025/10/12`、複数日の写真がある場合は `2025/10/10 〜 2025/10/12`）を訪問日に反映」** ワンタップ提案チップを表示する（ユーザーの同意なしに日付を自動上書きしない）。<br>・Canvas への再描画・再エンコードにより、保存される圧縮画像・サムネイルから **GPS 座標・撮影機材・シリアル番号等の全 EXIF メタデータを確実に除去** する。 |
| **F-Photo-04** | **キャプション入力・並び替え・削除** | ・添付中の各写真に対し、任意の **キャプション（最大 200 文字、制御文字不可）** を入力・編集できる。<br>・ボタン操作（左へ／右へ、または先頭を代表に設定）で写真の並び順を変更でき、**1 枚目の写真をそのログ（および地点一覧）の代表写真** とする。<br>・添付写真の個別削除ができる。<br>・フォーム保存確定前に追加した画像は一時メモリ上にのみ保持し、フォームを「キャンセル」した場合は IndexedDB へ書き込まず一時 Object URL を解放する（孤児データを作らない）。 |

### 4.2 写真の閲覧・一覧統合（`F-PhotoView`）

| 要件ID | 機能名 | 要件内容 |
| :--- | :--- | :--- |
| **F-PhotoView-01** | **詳細シートでのサムネイル一覧表示** | `SpotDetailSheet` の各ログカード内に添付写真（最大 5 枚）のサムネイルグリッドを表示する。キャプションが設定されている場合はサムネイル下またはツールチップ等で視認可能とし、ローカル未取得（Drive 未同期）の写真には読み込み状態または取得トリガーを表示する。 |
| **F-PhotoView-02** | **拡大ライトボックス閲覧** | サムネイルをタップするとフルスクリーン拡大モーダル（`PhotoLightbox`）を開く。<br>・1,600px 閲覧用画像（未キャッシュ時はオンデマンド取得して表示）を大きく表示し、写真キャプション・撮影日時・現在の位置（例: `2 / 5`）を表示する。<br>・同一ログ内の複数写真を **前へ／次へボタン、左右矢印キー、横スワイプ** で切り替えられる。<br>・**単体画像の端末保存／共有**（モバイル共有シート / ダウンロード）に対応する。<br>・Esc キー、閉じるボタン、背景タップで閉じることができ、表示中は Service Worker の自動更新リロードを抑止する。 |
| **F-PhotoView-03** | **登録地点一覧カード統合 & キャプション検索** | `SpotNavDrawer` の「登録地点」一覧カードにおいて、写真を持つ地点には **代表写真（最新ログの先頭写真）のサムネイル** と **地点内の総写真枚数バッジ（例: `📷 4`）** を表示する。<br>・**通信最適化原則**: ローカル IndexedDB に未キャッシュの写真について、一覧画面を開いただけで Google Drive API を一斉連打・自動ダウンロードしない。未キャッシュ時は枚数バッジとアイコンプレースホルダのみを表示し、ユーザーが詳細シートを開いて取得した後、または一括ダウンロード完了後にサムネイルを表示する。<br>・一覧のキーワード絞り込み対象に、地点名・住所補助・メモ本文に加えて **写真のキャプション** を含める。 |

### 4.3 ローカル永続化・Google Drive 同期・バックアップ（`F-CloudPhoto`）

| 要件ID | 機能名 | 要件内容 |
| :--- | :--- | :--- |
| **F-CloudPhoto-01** | **IndexedDB 原子的保存・Undo 保護・孤児 GC・容量表示** | ・新規写真を含む登録・更新時は、IndexedDB（`visit3d_db`）の `app_state` ストアと `photos` ストアを **単一トランザクションで原子的コミット** し、「メタデータだけ保存されて画像が無い」不整合を防止する。<br>・写真付きログや地点を削除した場合、あるいは Drive 復元／JSON インポートで上書きした場合でも、1 世代 Undo 機能（`restoreUndoSnapshot`）で写真を完全復元できるよう、直ちに画像 Blob を物理削除しない。`appState.spots` と `appState.undo?.spots` の **双方から参照が外れた写真 ID のみを自動 GC** で削除する。<br>・`CloudSyncDialog` 内に、端末内の保存写真枚数・概算ストレージ使用量（および `navigator.storage.estimate()` による端末全体の参考使用状況）を表示する。 |
| **F-CloudPhoto-02** | **Google Drive への写真保存（レジューム・重複防止）** | 「Drive に保存」実行時、以下の順序で安全に同期する：<br>1. **競合検知先行**: まず `visit-records.json` の更新有無を確認し、他端末更新との競合がある場合は写真アップロードやレコード上書きを行わず競合解決ダイアログを提示する。<br>2. **写真アップロード**: ローカルにあり `driveFileId` 未付与の写真本体（1,600px）を、`3D Visit Record/photos/` フォルダへ **並列上限 3 本** でアップロードする（進捗表示：`写真をアップロード中 (3/8)...`）。`photos/` 内に同一 `checksumSha256` の既存ファイルがあれば重複アップロードを省略しその ID を再利用する。<br>3. **途中中断レジューム**: 1 枚アップロード完了するごとに該当写真の `driveFileId` をローカル状態へ逐次反映するため、通信断等で途中失敗しても次回保存時は未アップロード分のみから再開できる。<br>4. **記録 JSON 保存**: 全写真への `driveFileId` 付与が完了した後、既存の 5 世代スナップショット退避付きで `visit-records.json` を保存する。<br>5. **未保存インジケーター**: `driveFileId` 未付与の写真が 1 枚でも存在する場合はヘッダーおよび同期ダイアログに「未保存の変更あり」を表示する。 |
| **F-CloudPhoto-03** | **オンデマンド取得 & 任意の一括ダウンロード** | ・**復元時の高速起動**: 「Drive から復元」時は `visit-records.json` のメタデータのみを即時ダウンロード＆適用し、写真本体は一括自動ダウンロードしない。<br>・**詳細表示時のオンデマンド取得**: 復元後の別端末等で地点詳細シートを開いた際、ローカル `photos` ストアに存在せず `driveFileId` を持つ写真があれば、Google 接続済み（有効トークン保持）なら自動で Drive から本体を取得し、端末内で 320px サムネイルを再生成して IndexedDB へキャッシュ保存・表示する。未接続時はサムネイル枠に「Drive から写真を読み込む」アクションを表示し、タップでサインイン・取得を実行できる。オフライン時や Drive 上から写真ファイルが削除済み（404）の場合は、無限リトライせず専用プレースホルダで案内する。<br>・**任意の一括ダウンロード**: `CloudSyncDialog` に **「未取得の写真をすべてダウンロード（残り N 枚 / 約 X MB）」** ボタンを配置し、事前にオフライン閲覧用へ一括キャッシュできる（進捗バー表示・キャンセル中断・途中再開に対応）。 |
| **F-CloudPhoto-04** | **マージ規則の v2 対応（削除・並び替えの同期）** | 複数端末間の復元マージ（`visitMerge`）において、v2.0 以降が出力した記録データ（`photoSyncVersion: 2`）を取り込む場合は、同一 `entry.id` で `updatedAt` が新しい側の `photos` 配列を正としてそのまま採用する。これにより「別端末で写真を 1 枚削除／全削除／並び替え／キャプション編集した変更」がマージ時に正しく反映され、削除済み写真が復活しないようにする（v1 旧バージョン JSON からの取り込みのみ従来の後方互換保護を維持）。復元前の差分プレビューでは、地点・ログ件数に加え、写真枚数の増減見込みを確認できるようにする。 |
| **F-CloudPhoto-05** | **Drive 上の不要写真の自動ゴミ箱整理** | 「Drive に保存」で `visit-records.json` の保存が正常完了した後、`3D Visit Record/photos/` 配下にあるファイルのうち現行の `spots` のどのログからも参照されなくなった旧写真ファイルを検出し、**自動で Google Drive のゴミ箱へ移動（`trashed: true`）** する。<br>・完全物理削除（`DELETE`）ではなくゴミ箱移動とすることで、誤操作や直近の `snapshots/` 世代との参照不整合が起きても Google Drive のゴミ箱から 30 日間復元可能とする。<br>・ゴミ箱移動処理の一部が通信エラー等で失敗しても記録本体の保存成功は妨げず、次回保存時に残りを整理する。 |
| **F-CloudPhoto-06** | **ローカル JSON バックアップの位置づけ明記** | 従来の JSON ファイル書き出し／読み込みはテキスト・メタデータのみを対象とする仕様を維持し、`CloudSyncDialog` 上の JSON バックアップセクションに **「※写真ファイル本体は JSON ファイルには含まれません。写真を別端末へ引き継ぐ場合は Google Drive 保存をご利用ください」** と明記する。 |

## 5. 非機能要件

| 分類 | 要件内容 |
| :--- | :--- |
| **パフォーマンス・応答性** | ・一覧カードや詳細シートのサムネイルは 320px 圧縮画像を用い、スクロール・シート展開の 60fps および INP 200ms 以内を損なわない。<br>・写真圧縮および SHA-256 算出は非同期処理とし、複数枚選択時も UI スレッドが長時間フリーズしないようにする。 |
| **モバイルブラウザ（特に iOS Safari）メモリ耐性** | ・高画素スマホ写真（1,200万〜4,800万画素級）を複数枚同時選択した場合でもメモリ不足でタブがクラッシュしないよう、リサイズ圧縮は **1 枚ずつ直列処理** し、各枚完了ごとに Canvas サイズを `0x0` へ縮小解放し不要な Bitmap/Image を破棄する。<br>・WebP エンコード非対応環境を検出し、確実に JPEG へ自動フォールバックする。<br>・表示用の `URL.createObjectURL()` は参照管理キャッシュで一元管理し、アンマウントや画面遷移時に確実に `revokeObjectURL()` してメモリリークを防ぐ。 |
| **ストレージ・通信効率** | ・1 枚あたりの目標容量は本体 約 200〜350 KB・サムネイル 約 20〜40 KB とし、1,000 枚蓄積しても端末内約 300〜400 MB 程度に収める。<br>・`QuotaExceededError` 発生時は既存データを一切破損させず、不要写真整理または容量不足をユーザーへ明示案内する。<br>・Drive からのオンデマンド取得は同一写真 ID への重複リクエストを統合（デデュプリケート）し、通信量と API レート消費を抑える。 |
| **データ整合性・耐障害性** | ・`app_state` と `photos` の保存を単一 IndexedDB トランザクションで行い、途中中断による不整合をなくす。<br>・Drive 上の写真同期は `driveFileId` の逐次保存によるレジュームと、`checksumSha256` による重複アップロード防止を備える。<br>・ゴミ箱移動は `visit-records.json` 保存成功後にのみ実行し、競合中の未確定状態で他端末の写真を誤ってゴミ箱へ送らない。 |
| **セキュリティ・プライバシー** | ・SVG 拒否＋Canvas 再エンコードによる画像無害化（アクティブスクリプト・悪意あるペイロード除去）を徹底する。<br>・EXIF GPS・撮影機材等のメタデータは保存画像へ一切残さない。<br>・OAuth スコープは引き続き `https://www.googleapis.com/auth/drive.file` のみに限定し、利用者の他の Drive ファイルや Google フォトへ一切アクセスしない。<br>・CSP は `img-src 'self' blob: data:` を許容し、生成した `blob:` URL の安全な描画と外部任意画像URL読み込み禁止を両立する。 |
| **運用コスト・インフラ** | ・画像変換・EXIF 解析・サムネイル生成・保存・取得のすべてをクライアントブラウザとユーザー自身の Google Drive 間で完結させ、開発者側のサーバー維持費・ストレージ課金ゼロを維持する。 |

## 6. v2.0 受け入れ基準（完了条件）

1. **写真添付・圧縮・EXIF 提案・永続化**:
   - 訪問済み地点の新規登録・再訪記録追加・既存訪問ログ編集・予定→訪問済み確定の各導線から、複数枚（最大 5 枚/ログ）の写真を選択・キャプション入力・並び替え・削除できること。
   - iOS Safari 相当（WebP 非対応時 JPEG フォールバック）を含むモダンブラウザで本体（長辺 1,600px 以下）およびサムネイル（長辺 320px 以下）が生成され、リロード後も IndexedDB から再表示されること。
   - 撮影日時 EXIF を持つ写真を追加した際、撮影日（複数日なら期間）の訪問日反映提案が提示され、出力画像から EXIF GPS 情報が除去されていること。
   - SVG ファイルおよび 25 MB 超または 6 枚目以降の追加が適切に拒否・案内されること。
2. **閲覧体験・検索**:
   - 詳細シート内のサムネイルからライトボックスが開き、前後切替・キーボード矢印/Esc・単体保存/共有が動作すること。
   - 登録地点一覧カードに代表サムネイルと総写真枚数バッジが表示され、キャプション文字列で地点を絞り込み検索できること（未キャッシュ地点の一覧表示時に Drive API を連打しないこと）。
3. **Google Drive 保存・レジューム・自動ゴミ箱整理**:
   - 写真付き地点を Google Drive へ保存すると `3D Visit Record/photos/` へ本体画像がアップロードされ、`visit-records.json` へ `driveFileId`・`checksumSha256` が保存されること。
   - アップロード途中で通信失敗した場合でも、次回保存時に成功済み写真の再送をスキップして残りからレジュームできること。
   - 写真を削除した状態で再度「Drive に保存」を完了すると、どの記録からも参照されなくなった Drive 上の写真ファイルが自動でゴミ箱（`trashed: true`）へ移動されること。
4. **別端末復元・オンデマンド取得・一括ダウンロード**:
   - 別端末（またはローカル初期化状態）から「Drive から復元」した直後はメタデータのみ即座に反映され、詳細シートを開くと未キャッシュ写真がオンデマンドで Drive から取得・サムネイル再生成・IndexedDB キャッシュ・表示されること。
   - 同期ダイアログの「未取得の写真をすべてダウンロード」ボタンから未取得写真を一括取得でき、進捗表示および途中キャンセルが機能すること。
5. **削除同期・Undo 保護・ローカル整合**:
   - 端末 A でログの写真を削除して Drive に保存し、端末 B でマージ復元した際に、端末 B 側でも該当写真が削除された状態になること（v1 空配列保護による復活が起きないこと）。
   - 復元・インポート直後に「元に戻す（Undo）」を実行した場合、復元前の地点データとともに写真画像も欠損なく再表示されること。
   - フォームのキャンセル時や、写真・地点削除後に Undo が不要・上書きされた際、不要な写真 Blob が IndexedDB に蓄積せず GC されること。
6. **プライバシー・セキュリティ**:
   - 3D 視点共有 URL に写真メタデータ・ID・キャプション等が含まれないこと。
   - `/privacy` ページに写真データのローカル圧縮・EXIF 除去・Drive 保存方針が明記されていること。
